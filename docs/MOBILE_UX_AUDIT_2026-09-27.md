# Mobile UX audit — SedChar.AI

วันที่ตรวจ: 27 กันยายน 2026  
ขอบเขต: `/` (Single-Char) และ `/multi` (Rubii Multi-Char)  
สถานะ: **เอกสารตรวจสอบและข้อเสนอเท่านั้น ยังไม่ได้แก้ UI หรือข้อมูลผู้ใช้**

## วิธีตรวจและข้อจำกัด

- เปิดแอปจาก dev server ในเบราว์เซอร์จำลองที่ viewport **390 × 844 CSS px**; ตรวจ DOM, ขนาดปุ่ม, ลำดับหน้าจอ และเส้นทางที่กดได้โดยไม่กรอก/ลบ/บันทึกข้อมูล
- อ่านโค้ดของเมนู ฟอร์ม พรีวิว คลัง และหน้าต่างเข้าสู่ระบบประกอบผลบนหน้าจอ
- ยังไม่ได้ทดสอบด้วยโทรศัพท์จริง, แป้นพิมพ์บนจอ, VoiceOver/TalkBack, ผู้ใช้ที่มีข้อมูลเต็ม, บัญชี Free/Premium หรือการบันทึกและส่งออกจริง
- คำว่า **ยืนยัน** หมายถึงพบใน UI ที่เปิดจริงและ/หรือมีโค้ดชี้สาเหตุ; **ต้องพิสูจน์เพิ่ม** หมายถึงพบความเสี่ยงจากโค้ดแต่ยังไม่จำลองสถานการณ์นั้น

## สรุปตามความสำคัญ

| ลำดับ | จุด | สถานะ | ผลต่อผู้ใช้ |
|---|---|---|---|
| P0 | `/multi` ไม่มีทางเปิดเมนูหมวดบนมือถือ | ยืนยัน | ไป Lore, Routes, Main Characters, Cast Rules และ Preview/Export ไม่ได้ |
| P1 | ฟิลด์ Multi-Char ไม่มีชื่อที่ผูกกับช่องกรอก | ยืนยัน | ผู้ใช้ screen reader ได้ยินตัวอย่างแทนชื่อฟิลด์; แตะชื่อฟิลด์แล้วไม่โฟกัสช่อง |
| P1 | ปุ่มหลักหลายจุดเล็กและใช้ไอคอนล้วน | ยืนยัน | แตะพลาดและหาคำสั่งบันทึก/ส่งออกยาก |
| P1 | ตัวเลือกแพลตฟอร์มใน Preview ใช้ `div` คลิกได้คู่กับ checkbox | ยืนยันจาก UI และโค้ด | แยกความหมาย “ดูแท็บ” กับ “รวมในการแปลง” ยาก; ใช้คีย์บอร์ดเปิดแท็บไม่ได้ |
| P2 | หน้ากรอก Single-Char แสดงคำชวนเข้าสู่ระบบซ้ำในพื้นที่เขียน | ยืนยัน | เนื้อที่สำหรับงานหลักลดลงและลำดับความสนใจสับสน |
| P2 | หน้าต่างเข้าสู่ระบบ/คลังยังขาดความหมาย modal และต้องตรวจจอเตี้ย | ส่วนหนึ่งยืนยัน; จอเตี้ยต้องพิสูจน์เพิ่ม | การนำทางด้วย screen reader/คีย์บอร์ดและการเข้าถึงปุ่มท้ายฟอร์มอาจมีปัญหา |

## รายละเอียดที่ยืนยันแล้ว

### M-01 — เมนูหมวด Multi-Char เปิดไม่ได้บนมือถือ (P0)

- **เส้นทาง:** `/multi` ที่ 390 × 844
- **สิ่งที่เห็น:** มีเพียง World Setting; ไม่มีปุ่ม Hamburger หรือแท็บสำหรับเปลี่ยนหมวดใน header หรือเนื้อหา
- **สาเหตุในโค้ด:** sidebar แสดงเมื่อ `md` ขึ้นไป (`src/components/rubii-multi/RubiiMultiWorkspace.tsx:202`) และ drawer มือถือแสดงเฉพาะเมื่อ `isMobileDrawerOpen` เป็นจริง (`:279`) แต่ state เริ่ม `false` (`:80`) และทุกจุดที่เรียก `setIsMobileDrawerOpen` ตั้งเป็น `false` (`:285`, `:302`, `:319`)
- **ผล:** งานหลัก 5/6 หมวดเข้าถึงไม่ได้บนมือถือ รวมทั้งหน้าส่งออก แม้ระบบจะมีเนื้อหาหมวดนั้นอยู่
- **ข้อเสนอให้พิจารณา:** เพิ่มปุ่มเปิดเมนูที่เห็นชัดใน header มือถือ; ระบุหมวดปัจจุบัน; ให้ drawer ปิดได้ด้วยปุ่ม, backdrop และ Escape; ตรวจสถานะ focus เมื่อเปิด/ปิด
- **เกณฑ์รับ:** ที่ 320–430 px ผู้ใช้แตะจาก World ไปแต่ละหมวดทั้ง 6 และกลับได้โดยไม่เสีย draft; ชื่อหมวดปัจจุบันอ่านได้

### M-02 — ชื่อฟิลด์ Multi-Char ไม่ผูกกับ control (P1)

- **เส้นทาง:** `/multi` → World Setting
- **หลักฐาน:** ช่องกรอก 7 ช่องที่มองเห็นมี `labels.length = 0`, ไม่มี `id` และไม่มี `aria-label`; accessibility tree แสดง textbox ด้วยข้อความตัวอย่าง เช่น “เช่น Aethelgard...” แทน “ชื่อโปรเจกต์ / ชื่อเรื่อง”
- **จุดโค้ด:** `src/components/rubii-multi/WorldSettingSection.tsx:35-127`; รูปแบบ label ที่ไม่ได้ผูกกับช่องยังปรากฏใน Lore, Routes, Main Characters, Cast Rules และฟอร์มบันทึกโปรเจกต์
- **ผล:** ผู้อ่านหน้าจอและผู้ใช้ voice input ระบุช่องยาก; placeholder หายไปเมื่อพิมพ์ ทำให้ตรวจทานฟอร์มยาก
- **ข้อเสนอให้พิจารณา:** ผูก `htmlFor`/`id` หรือห่อ control ใน label ที่ถูกต้อง; ใช้ `aria-describedby` สำหรับคำอธิบายและเงื่อนไข; คง placeholder เป็นตัวอย่างเท่านั้น
- **เกณฑ์รับ:** ทุก input/textarea/select อ่านชื่อและคำอธิบายได้ถูกต้องเมื่อ focus; แตะข้อความ label แล้วช่องรับ focus

### M-03 — ปุ่มใน header และ Preview มีพื้นที่แตะเล็ก (P1)

- **หลักฐานที่ 390 × 844:** header `/multi` ปุ่มคลังประมาณ 39 × 27 px, ล้างโปรเจกต์ 27 × 32 px, เปลี่ยนธีม 31 × 36 px; header `/` ปุ่ม App Switcher 32 × 32 px และเข้าสู่ระบบ 93 × 28 px; ใน Preview ปุ่ม fullscreen ประมาณ 27 × 27 px, แก้ไข/คัดลอกสูง 25 px
- **ผล:** ปุ่มถี่และเล็กเมื่อใช้นิ้ว โดยเฉพาะคำสั่งล้างที่อยู่ใกล้คำสั่งอื่น
- **ข้อเสนอให้พิจารณา:** ขยายพื้นที่กดจริงให้ใกล้ 44 × 44 CSS px โดยไม่จำเป็นต้องขยายไอคอน; เพิ่มระยะห่างและตรวจตำแหน่งคำสั่งที่มีผลต่อข้อมูล
- **เกณฑ์รับ:** จุดแตะสำคัญสูง/กว้างอย่างน้อย 44 px หรือมีระยะว่างทดแทนที่ตรวจได้; ไม่มีการแตะข้างเคียงโดยง่ายบนจอ 320 px

### M-04 — คำสั่งสำคัญพึ่งไอคอน/tooltip (P1)

- **เส้นทาง:** `/multi` header และ `/` → ดูผลลัพธ์
- **สิ่งที่เห็น:** คลัง Multi-Char และล้างโปรเจกต์เป็นไอคอนล้วนบนมือถือ; ปุ่มส่งออกใน Single-Char Preview เป็นไอคอนล้วนและใน accessibility tree เป็น `button` ไม่มีชื่อ; ปุ่มคลังแสดงไอคอนล้วน แม้มี `title`
- **จุดโค้ด:** `RubiiMultiWorkspace.tsx:138-170`, `PlatformPreview.tsx:435-456`
- **ผล:** ผู้ใช้ต้องเดาความหมายก่อนลองแตะ; hover tooltip ใช้ไม่ได้ด้วยนิ้ว; screen reader ไม่ได้ชื่อปุ่มส่งออก
- **ข้อเสนอให้พิจารณา:** ให้คำสั่งหลักอย่างบันทึก/ส่งออกมีข้อความบนมือถือหรือ label ใกล้ปุ่ม; ให้ปุ่มไอคอนทุกตัวมี accessible name ที่สื่อการกระทำ; คำสั่งล้างต้องสื่อชัด
- **เกณฑ์รับ:** ผู้ใช้ใหม่ระบุทางบันทึกและส่งออกได้จากหน้าจอโดยไม่ต้องเดาไอคอน; screen reader อ่านชื่อทุกปุ่มได้

### M-05 — แท็บแพลตฟอร์มกับ checkbox ใน Preview สื่อความหมายซ้อนกัน (P1)

- **เส้นทาง:** `/` → ดูผลลัพธ์
- **สิ่งที่เห็น:** Purrpaw, Rubii, Khui AI, Master MD เป็นข้อความใน generic container โดยมี checkbox อยู่หน้าแต่ละชื่อ; กดแถวเพื่อดูพรีวิว แต่กด checkbox เพื่อเปิด/ปิดการแปลง
- **จุดโค้ด:** `src/components/preview/PlatformPreview.tsx:380-420` ใช้ `div onClick` สำหรับเปลี่ยนแท็บ ไม่ใช่ button/tab; checkbox เล็ก `w-3.5 h-3.5`
- **ผล:** มือใหม่อาจคิดว่าติ๊กเลือกคือเปลี่ยนแท็บ หรือปิดแพลตฟอร์มโดยไม่ตั้งใจ; keyboard/screen reader ไปยังแท็บโดยตรงไม่ได้
- **ข้อเสนอให้พิจารณา:** แยกการเลือกหน้าพรีวิวกับการรวมใน export ให้เป็น control คนละชุดและมีคำอธิบาย; ใช้ semantics ของ tab/button และ checkbox ที่มีชื่อชัด
- **เกณฑ์รับ:** เปลี่ยนพรีวิวด้วย touch, keyboard และ screen reader ได้; ผู้ใช้ระบุได้ว่าติ๊กถูกมีผลกับการแปลง/ส่งออกอย่างไร

### M-06 — Single-Char ซ้ำคำชวนเข้าสู่ระบบในพื้นที่งาน (P2)

- **เส้นทาง:** `/` → สร้าง/แก้ไข → โหมดกรอกรวดเดียว (guest)
- **สิ่งที่เห็น:** แถบเครื่องมือมี “🔒 เข้าสู่ระบบรับ 15 ครั้ง/วัน” และใต้แถบมี banner “เข้าสู่ระบบเพื่อใช้งาน Auto-Parser...” พร้อมปุ่มเข้าสู่ระบบอีกครั้ง; ที่ 390 px กลุ่มบนแถบเครื่องมือห่อบรรทัดและกินความสูงราว 53 px
- **จุดโค้ด:** `src/components/form/SingleBoxInput.tsx:167-227`
- **ผล:** พื้นที่เริ่มเขียนถูกดันลง; ผู้ใช้อาจไม่เห็นความต่างระหว่างการกรอกเองกับ Auto-Parser ที่ล็อก
- **ข้อเสนอให้พิจารณา:** ลดการแจ้งซ้ำและอธิบายขั้นตอนหลักที่ guest ใช้ได้ตรงจุด; จัดลำดับการกระทำหลักให้เด่นกว่าข้อความโปรโมต
- **เกณฑ์รับ:** viewport 390 × 667 แสดงจุดเริ่มพิมพ์และการกระทำต่อไปโดยไม่ต้องผ่านข้อความซ้ำหลายชั้น

### M-07 — ตัวเลือกรายชื่อตัวละครหลักไม่มี semantics ของปุ่ม (P2)

- **เส้นทาง:** `/multi` → Main Characters (ตรวจโค้ด; UI มือถือถูก M-01 บล็อก)
- **จุดโค้ด:** `src/components/rubii-multi/MainCharactersSection.tsx:102-155` แถวตัวละครเป็น `div onClick` ไม่มี `role`, `tabIndex` หรือ keyboard handler; ปุ่มลบในแถวมีขนาด 28 × 28 px
- **ผล:** เมื่อปลดล็อกเมนูแล้ว ผู้ใช้คีย์บอร์ด/เทคโนโลยีช่วยเหลืออาจเลือกตัวละครอื่นไม่ได้ และปุ่มลบแตะพลาดง่าย
- **ข้อเสนอให้พิจารณา:** ทำแถวเลือกเป็น button/tab ที่มีสถานะเลือก และแยกปุ่มลบที่กดได้สะดวกพร้อมการยืนยันที่เหมาะสม
- **เกณฑ์รับ:** สลับตัวละครด้วยคีย์บอร์ดและ screen reader ได้; การลบไม่เกิดจากการแตะพลาด

### M-08 — หน้าต่างยังไม่ประกาศเป็น dialog (P2)

- **เส้นทาง:** `/multi` → คลังโปรเจกต์; `/multi` → เข้าสู่ระบบ
- **หลักฐาน:** เปิดหน้าต่างได้บนมือถือ แต่ accessibility tree แสดงหัวข้อและปุ่มต่อจาก `main` โดยไม่มี `dialog`; markup ของ `MultiCharLibraryModal.tsx:135-142` และ `AuthModal.tsx:90-92` ไม่มี `role="dialog"`/`aria-modal`
- **ผล:** ผู้ใช้ screen reader อาจไม่ทราบว่าบริบทเปลี่ยนเป็นหน้าต่าง; ลำดับ focus และการกลับไปปุ่มเดิมยังต้องตรวจ
- **ข้อเสนอให้พิจารณา:** กำหนด semantics dialog, ชื่อที่ผูกกับ heading, จัด focus เมื่อเปิด/ปิด และจำกัดการเดิน focus ให้อยู่ใน modal
- **เกณฑ์รับ:** VoiceOver/TalkBack ประกาศชื่อหน้าต่าง; Tab ไม่หลุดไปเนื้อหาด้านหลัง; ปิดแล้ว focus กลับจุดเปิด

## ความเสี่ยงที่ต้องพิสูจน์เพิ่มก่อนตัดสินใจแก้

| จุด | เหตุที่สงสัย | วิธีพิสูจน์ |
|---|---|---|
| หน้าต่างเข้าสู่ระบบบนจอเตี้ย/เมื่อคีย์บอร์ดขึ้น | `AuthModal.tsx:91-92` ไม่มี `max-height` หรือ scroll ภายใน; wrapper อยู่กลางจอ | ทดสอบ 320 × 568, 390 × 600 และแป้นพิมพ์จริงทั้ง signin/signup/reset; ตรวจปุ่มส่งและปิดยังแตะถึง |
| scroll ของ workspace เมื่อคีย์บอร์ดขึ้น | ทั้ง `/` และ `/multi` ใช้ `h-screen` และ `overflow-hidden`; scroll อยู่ใน panel ลูก | โฟกัสช่องท้าย ๆ, เปิดคีย์บอร์ด, หมุนจอ; ตรวจ caret/ปุ่มไม่ถูกบังและเลื่อนกลับได้ |
| การบันทึก draft/สถานะสำเร็จใน Multi-Char | autosave ลง localStorage แต่ข้อความ “บันทึก Draft อัตโนมัติ” อยู่ใน sidebar desktop | กรอกข้อมูลทดลองในโปรไฟล์แยก, รอ, refresh, สลับหมวด/หน้า; ตรวจ feedback บนมือถือและความเข้าใจระหว่าง autosave กับคลังโปรเจกต์ |
| Main Characters, Lore, Routes, Cast Rules, Export | เมนู M-01 บล็อกการเข้าถึง UI เหล่านี้ในมือถือ | หลังมีทางเข้าแล้วตรวจทุก state: ว่าง, หลายรายการ, ครบ 10 ตัว, ข้อความยาว, validation, ลบ, ส่งออก |
| การซูมข้อความ/ขนาดฟอนต์ระบบ | หลายจุดใช้ `text-[10px]`/`text-[11px]` และ panel จำกัดความสูง | ทดสอบ text scale 200%, zoom 200%, 320 px; ดูข้อความตัด/ปุ่มซ้อน/scroll แนวนอน |
| คลังตัวละคร Single-Char | modal สูง 90vh และมี scroll ภายใน | ทดสอบรายการยาว, filter, เพิ่ม/แก้, ปุ่มท้ายฟอร์ม, คีย์บอร์ดบนจอและ focus |
| สีและสถานะเลือก | ใช้สี/ความจางระบุแท็บและ state หลายจุด | ตรวจ contrast ใน light/dark และเมื่อเปิด high contrast/reduced motion; ต้องมีตัวบ่งชี้ที่ไม่พึ่งสีอย่างเดียว |

## ลำดับทำงานที่เสนอเมื่ออนุมัติให้แก้ในภายหลัง

1. ปลดบล็อกเมนู `/multi` (M-01) แล้วตรวจครบ 6 หมวดบนมือถือ
2. แก้ชื่อ control และ semantics ของ navigation/modal (M-02, M-05, M-07, M-08)
3. ขยายจุดแตะและทำคำสั่งบันทึก/ส่งออกให้เห็นชัด (M-03, M-04)
4. ลดความแน่นของหน้าเขียน Single-Char และทดสอบจอเตี้ย/คีย์บอร์ด (M-06 และความเสี่ยง)
5. เดินเช็กลิสต์ทุก state พร้อมข้อมูลทดลองในโปรไฟล์แยก ก่อนปล่อยใช้งาน

เอกสารนี้ยังไม่ใช่ผลทดสอบครบทุกสถานการณ์: M-01 ปิดทางเข้าห้าหมวดบนมือถือ จึงต้องตรวจ UI ของหมวดเหล่านั้นซ้ำหลังแก้ทางนำทางก่อนสรุปว่าประสบการณ์ Multi-Char พร้อมใช้
